# Unity 游戏框架长期目标

> 本文提供项目方向和决策边界，交给 Unity AI Agent 使用。
> 本文不预先规定具体类名、目录结构、接口或实现方案。

## 0. Agent 的执行权限和输出形式

默认情况下，Unity AI Agent 只读取和分析当前项目，不直接修改项目文件。

Agent 的默认工作内容是编写“框架代码设计文档”，包括：

- 当前代码已经提供的能力。
- 当前问题和形成原因。
- 建议新增或调整的框架职责。
- 涉及的脚本路径。
- 类、字段、方法和调用关系的设计。
- 代码应该修改的位置和修改目的。
- 需要保留的现有行为。
- 最小验证方式。

未经用户明确授权，Agent 不得：

- 直接修改、替换或删除 C# 脚本。
- 直接修改 Unity 场景、Prefab、材质或资源配置。
- 直接修改项目设置、包配置或目录结构。
- 直接创建可以影响当前项目运行结果的代码文件。

用户需要根据设计文档手动编写和验证框架代码。只有用户明确要求“直接修改项目”时，Agent 才进入代码修改流程，并且仍然要先说明修改范围。

设计文档中的代码应服务于说明当前方案。对于尚未确认的实现，不写成看起来已经存在的完整代码，也不把伪代码当作当前项目代码。

## 1. 框架定位

当前项目的目标是发展成一个可复用的 Unity 游戏框架。

它应该服务于多个游戏项目，示例项目只用于验证框架能力，示例项目中的业务逻辑、测试页面和临时写法不应反过来决定框架结构。

框架的长期价值不在于功能数量，而在于：

- 模块职责清楚。
- 模块之间依赖关系可控。
- 常见问题有稳定的解决方式。
- 新项目可以按需接入，而不是整体搬运业务代码。
- 复杂功能经过成熟方案调查后再决定是否加入。

## 2. 长期建设方向

框架长期可以覆盖以下方向：

### 基础运行能力

- 生命周期和启动流程。
- Architecture、Model、System、Controller 等基础协作方式。
- 事件、命令、查询和状态通知。
- 依赖注册和模块初始化。
- 场景切换、全局对象和跨场景服务。

### 资源和数据能力

- 资源加载和释放。
- Prefab、配置、表格和其他游戏资源的访问。
- 数据保存、读取和版本迁移。
- 异步操作、失败处理和生命周期管理。

### 表现层能力

- UGUI。
- UI Toolkit。
- 页面流程、弹窗、层级和生命周期。
- 动画、音频、输入和其他表现服务。
- 高频表现对象的复用。

### 游戏业务支撑能力

- 场景和流程管理。
- 输入和操作映射。
- 状态机或流程控制。
- 实体、角色、战斗等可复用基础能力。
- 网络、热更新或平台适配等实际需求出现后的扩展。

### 工具和工程能力

- 示例项目。
- 编辑器辅助工具。
- 日志、诊断和运行时观察。
- 模块文档。
- 必要的自动化验证。

以上是长期方向，不代表现在全部实现，也不代表每个项目都必须接入全部模块。

## 3. 当前阶段重点

当前阶段优先完善 UI 模块，因为它已经具备实际代码、示例场景和使用问题。

当前重点是把 UI 的实际边界和使用方式验证清楚，包括：

- 资源加载、实例创建和资源释放。
- 页面生命周期。
- Scene 和 Persistent 生命周期。
- 页面、弹窗、Tab、HUD、Toast 等不同 UI 需求的区分。
- 页面之间的前进、返回和直接跳转。
- UGUI Root 和层级管理。
- UGUI 与未来 UI Toolkit 之间应该共享哪些概念。
- 高频 UI 是否需要独立的复用方案。

UI 是当前优先级，不代表整个框架最终只围绕 UI 发展。

## 4. Agent 的工作目标

Unity AI Agent 接手任务时，应围绕以下问题工作：

1. 当前框架已经提供了什么能力。
2. 当前代码中哪些职责已经混在一起。
3. 用户遇到的实际问题属于哪个模块。
4. 是否存在成熟的 Unity、GitHub 或社区方案。
5. 成熟方案是否真的适合当前项目的 Unity 版本、资源系统和代码结构。
6. 应该直接接入、编写适配层，还是只吸收设计思路。
7. 当前最小的有效改动是什么。

Agent 应先调查和比较，再做设计决定。调查结果需要区分：

- 已经由当前代码验证的事实。
- 外部框架已经提供的能力。
- 根据现有信息作出的推断。
- 仍然需要验证的风险。

## 5. 设计决策原则

- 优先复用当前已经稳定的模块。
- 新增模块必须对应明确的问题或已经确认的需求。
- 先研究成熟方案，再决定自研范围。
- 采用成熟方案时，优先使用包或适配层，保留当前项目自己的边界。
- 参考别人的设计时，先分析它的前提、依赖和取舍，再决定是否适合当前项目。
- 代码量、抽象层和配置项都应与实际需求匹配。
- 示例项目用于验证框架，不作为框架业务代码的来源。
- 框架模块不应依赖某个具体游戏的角色、关卡、活动或 UI 名称。
- 需要兼容未来技术时，先保留清晰的边界，不提前实现没有需求的完整系统。
- 每次只推进一个可以验证的垂直功能。

## 6. 预期发展阶段

### 阶段一：理解和整理现状

建立当前模块清单，确认每个模块的职责、依赖和实际使用情况。

输出应包含：

- 当前已经完成的能力。
- 当前正在使用的能力。
- 存在的重复职责。
- 明确的缺口。
- 下一步最值得处理的问题。

### 阶段二：完成 UI 的可用闭环

以 UGUI 为当前主线，形成一条真实可用的流程：

```text
加载资源 -> 创建 UI -> 显示和交互 -> 页面切换 -> 返回或关闭 -> 释放资源
```

这一阶段重视边界和正确性，不追求一次加入所有 UI 功能。

### 阶段三：完善可复用的基础模块

根据实际项目需求，逐步整理资源、数据、场景、事件、输入、音频和其他基础服务。

每个模块都需要先确认复用价值，再决定是否进入框架。

### 阶段四：验证跨项目复用

在独立示例项目或第二个小型示例中验证：

- 框架是否依赖原测试项目。
- 模块是否能独立接入。
- 文档是否能让新项目正确使用。
- 删除业务代码后框架是否仍然成立。

### 阶段五：工程化和扩展

在多个模块和示例稳定后，再考虑编辑器工具、自动化验证、性能优化、UI Toolkit、对象池、热更新和平台适配等扩展。

## 7. 每次实施前的要求

在修改代码前，Agent 应先完成以下工作：

- 阅读交接文档和相关模块代码。
- 确认当前工作目录和实际使用的示例项目。
- 检查工作区是否存在用户未提交的修改。
- 明确本次只解决的一个问题。
- 找出将被修改的具体文件和代码位置。
- 调查是否存在可复用的成熟方案。
- 说明采用、适配或暂缓的理由。

如果只是解释、检查、比较或编写教学文档，应保持源代码不变。

如果需要修改代码，应保持改动范围清楚，并说明：

- 解决了什么问题。
- 保留了哪些旧行为。
- 新增了哪些行为。
- 哪些内容仍然属于后续阶段。

## 8. 文档目标

每份实施文档只需要包含：

1. 当前模块进度。
2. 本次要解决的问题。
3. 需要修改的文件路径和代码位置。
4. 具体修改内容及关键注释。
5. 最小验证方式。
6. 简短总结。

文档应服务于实际编码，不把尚未实现的伪代码、无关方案和重复解释混在当前步骤中。

## 9. 最终目标

最终希望得到的是一套：

- 可以被多个 Unity 项目复用。
- 可以逐模块接入。
- 有清晰生命周期和依赖关系。
- 能与成熟第三方方案协作。
- 能通过示例项目验证。
- 方便学习、维护和继续扩展。

框架的每个模块都应回答三个问题：

```text
它解决什么实际问题？
它依赖哪些已有能力？
它是否值得成为框架的一部分？
```

当前答案优先从 UI 模块开始验证，长期目标仍然是完整的 Unity 游戏框架。
